## Steps

1. **Env.** One optional variable, `ONMEETING_CREDENTIALS_ENCRYPTION_KEY` (32 base64 bytes), in t3-env + STATE.md's env list. There is **no** deployment-level onMeeting app, client id, secret, or webhook token to provision — that whole class of setup disappears with Zoom. Document the integration in TARGET `docs\integrations-onmeeting.md` as you go.
2. **onMeeting API client.** `integrations\onmeeting\`: raw `fetch` + **Zod-parsed** responses for `/user/api-keys`, `/auth/token`, `/user/rooms`, `POST /meeting`, `GET /meeting/{no}` (no new dependency — same approach as the Google integration, D122). Unwrapping the `results.data` envelope and building the `https://onmeeting.co/j/{meeting_no}` link are pure functions in their own module so they're unit-testable; the rest is `server-only`. **The provider's `join_url` is what gets stored** — the constructed `/j/` form is only a fallback for the create response, which returns a meeting number but no URLs. Provider error text never reaches the client and is never logged raw (D138).
3. **Connected accounts.** `features\system\live-classes\meeting-accounts\`: the connect mutation takes a display name + the admin's own onMeeting email and password, exchanges them for API keys, lists the account's rooms, and writes **one `meeting_accounts` row per room** (`active` immediately — there is no pending state without an OAuth round trip). A room's identity is `(organizationId, roomCode)` behind a **partial unique index over non-deleted rows**, and connecting is an **upsert**: reconnecting the same account — a retry, a rotated password, a second admin — refreshes the existing row rather than doubling the org's apparent capacity. A room missing from a later `/user/rooms` response is left alone, never retired, because sessions reference it. The password is used for one request and never persisted or logged; the keys are stored AES-256-GCM encrypted. `orgAdminProcedure` **and** rate-limited, because it accepts a password. Disconnect soft-deletes and clears the key columns.
4. **Session ↔ meeting linking, on demand.** `POST /meeting` has **no `start_time`** — a meeting lives in a room, not at a moment — so meetings are created when the class starts, not generated ahead by Inngest. `sessions.startMeeting` (assigned teacher or org admin, inside the session's meeting window) is idempotent: a session that already has a meeting returns its stored links; otherwise it reserves a free room under the per-organization advisory lock (a room hosts one live meeting at a time), creates the meeting, and stores `meetingNumber` / `joinUrl` / `startUrl`. Sessions in an org with no connected account stay **offline** gracefully and still schedule and display.
5. **Sessions UI.** Session list (per group + org agenda view): a "Start class" action for hosts, the participant join link for everyone else once the meeting exists, a clear "hasn't started yet" state before that, and status (upcoming/live/ended). `start_url` is host-only and never travels to a non-host.
6. **Attendance.** Per-session register, **marked by the teacher** — onMeeting exposes no webhooks and no participants endpoint, so there is nothing to detect attendance from. `markAttendance` already stamps `source: "manual"`. Per-trainee attendance feeds the Phase-5 progress view. Open questions that would restore automatic attendance are tracked in `docs\integrations-onmeeting.md` §7 for Mohamed to put to onMeeting support.
7. **Copy check.** Wherever Live Classes surfaces — in-app and on the landing pages — wording matches what is actually true: streaming/whiteboard/recording/screen-share happen **in onMeeting**; the system manages scheduling, links, and attendance. **No claim of automatic attendance, and no claim of recording links**, anywhere (blueprint rule 9).
8. **Tests.** vitest: envelope + error-shape parsing, join-URL construction, one-row-per-room connect, **reconnect updating rather than duplicating**, on-demand creation idempotency, and room reservation under contention. Org isolation on `meeting_accounts`. **The password's secrecy boundary is tested on every edge, not just the happy path**: it must not reach the persisted row, the thrown message on a rejected sign-in, the message on a provider outage, or the request URL — the last because a credential in a query string lands in access logs.
