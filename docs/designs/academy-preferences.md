## Problem Statement

Gateling-TMS should let each academy's owner shape how the system behaves ("settings, aka parameters") so one product serves both solo online teachers and larger academies with teams, without forking behavior in code per customer.

Today nothing like this exists. The `settings` table is deployment-wide by design (no `organizationId`, excluded from the org-isolation suite) and holds only the three Gateling Meetings integration keys. The only per-academy preferences are two fixed columns on `organizations`: `timeZone` and `currency`.

## Demand Evidence

- **One real user:** Mohamed's wife runs an online English academy on Gateling daily and keeps asking for more.
- **No payments yet**, from her or anyone else.
- **Her requests are mostly missing features, not preferences.** Things every academy would want the same way. So far no request shows two academies wanting opposite behavior, which is the only thing that justifies a setting.
- **No second academy named yet.**

Honest read: there's evidence the product is useful to one academy. There's no evidence yet that configurability is needed or that anyone will pay.

## Status Quo

Online English teachers run on **WhatsApp groups + Google Sheets/Excel + Zoom/Meet**. It's free and familiar, with no learning curve. Gateling beats it only where a whole chore disappears.

The chore Gateling killed for the reference academy: **scheduling + attendance**. That covers group schedules, generated sessions, class links, rescheduling and who showed up.

Market check: incumbents (Teach 'n Go from €69/mo, Teachworks, Tutorbase, Teamlilit) already ship scheduling, attendance, billing and "AI workflows". Schools name scheduling conflicts and chasing payments as their top two pains. None of those incumbents appears to target Arabic/RTL, EGP, Egyptian payment rails or WhatsApp-first academies. That is a likelier edge than configurability. It's a hypothesis until academy #2.

## Target User & Narrowest Wedge

- **Reference user:** the owner of a small online English academy in Egypt, currently her.
- **Wedge:** scheduling + attendance that replaces the WhatsApp/Sheets/Zoom loop. It's already built (weekly schedules → generated sessions → Gateling Meetings one-click join → teacher-marked attendance).

## Premises (agreed)

1. The reference academy is the default. Her way is the behavior every new academy gets with zero configuration.
2. A per-academy setting is added only when a second real academy wants different behavior. No speculative toggles.
3. Per-academy settings live in a new org-scoped layer (`organizationId`, tenant-isolated, covered by `test:isolation`), separate from the deployment `settings` table.
4. The typed-registry pattern of `system-settings-registry.ts` is reused: code → meaning, default, validation. No loose key-value bag.
5. The next milestone is academy #2 running scheduling + attendance, not a settings engine.

## Approaches Considered

- **A: Typed columns on `organizations`.** Rejected because each setting needs a migration, and the table turns into a junk drawer past about 8 preferences.
- **C: "Solo vs team" onboarding presets.** Deferred because preset contents are guesses without a second academy. It composes on top of B later, since a preset is a bundle of registry defaults.

## Recommended Approach: B, an org-scoped policy registry

### Data

New table `organization_settings`:

| column | type | notes |
|---|---|---|
| `id` | uuid | helper `id` |
| `organizationId` | uuid FK → organizations, cascade | tenant key |
| `code` | varchar(128) | registry code |
| `value` | jsonb | shape owned by the registry's Zod schema |
| `createdBy` / `updatedBy` | varchar (actor email) | helpers, audit |
| `createdAt` / `updatedAt` | timestamps | helpers |

- Unique `(organizationId, code)`.
- **No row means the registry default applies.** Resetting to default deletes the row.
- Schema-first, and the migration is generated (`npm run db:generate`), never hand-written.
- Add the table to the org-isolation suite (23 → 24 tenant-owned tables): A's update/reset never changes B's row, and A's list never returns B's values.

### Registry

`src/features/system/settings/lib/academy-settings-registry.ts` (Smaller arrangement, D1) sits beside the system registry and mirrors it:

- `code`: zero-padded, stable, never reused.
- `group`: e.g. `scheduling`, `attendance`, for grouping in the UI.
- `control` (R4): `{ kind: "boolean" } | { kind: "enum", options } | { kind: "number", min, max, step }`. One helper builds the value's Zod schema from it, so the UI never inspects Zod internals.
- `default`: a typed value, taken from the reference academy's behavior. It must parse under its control.
- `appliesTo` (R3): `"future"` (default: new records only) or `{ reapply: "<inngest event>" }`. A reapply save enqueues that event; rows are never rewritten inside the request.
- `labelKey` / `descriptionKey`: i18n keys in both `en.ts` and `ar.ts`.
- **`requestedBy`**: a comment naming the academy and the disagreement that justified the setting. It's enforced in review only (R5, accepted shortcut `dec-28099644`).

### Read path

- `readAcademySettings(db, organizationId)` (R2) runs one query for all rows of an org and returns a fully-typed, default-merged object. It works from tRPC, Inngest and Server Components. Unknown or retired codes are ignored.
- `getAcademySettings(organizationId)` is a `cache()` wrapper for Server Components only. Jobs read once per run and pass the values down.
- A stored value that fails its Zod parse falls back to the default **and is logged server-side** with org + code. It never throws into a user flow and never fails silently.

### Write path

- `settings.academy.update` / `settings.academy.reset` on `orgAdminProcedure`. Validate with the entry's control-built schema, then upsert on `(organizationId, code)`. `reset` deletes the row. A reapply entry enqueues its Inngest event **all-or-nothing** (design review 5A): if the enqueue fails, the value is not committed (or is rolled back). The row shows an inline Alert, "Nothing changed. Try again." (en + ar), and keeps the staged value so the owner can retry.
- Updates `updatedBy`.

### UI

- **Placement (design review 1A):** an "Academy preferences" section (group cards, see 8B) on the academy's Settings page (`/settings`, formerly `/organizations`; `organizations-settings-page.tsx`). It sits after `PlanUsageCard` and before `PublicShowcaseCard`, and is visible when `canManage` (admin). The server code stays in `features/system/settings` (D1); only the screen lives with the academy. The platform-level page is `/platform` ("Platform").
- Each control is rendered from its declared `control` (R4): boolean → switch, enum → select, number → input with bounds. The effect hint ("applies to new classes only" vs "updates existing classes") shows before save (R3).
- **Anatomy (design review 8B, Mohamed's choice over the recommended single card):**
  - An "Academy preferences" section heading (`h2`, `text-lg font-semibold`, matching "Members" on the same page) is followed by **one `Card` per group** (Scheduling, Attendance, ...).
  - Each group card has a `CardHeader` with the group title, an inline lucide icon (`size-4`, as on the Meetings card, not a colored tile) and a one-line `CardDescription`.
  - `CardContent` holds that group's rows, separated by `divide-y`.
  - Row: label (`font-medium`) and description (`text-sm text-muted-foreground`) at the start, the control at the end, and the effect hint underneath (muted for future-only; warning tone + icon for reapply).
  - The group cards are siblings in the section, never nested inside another card.
- **Labels + component map (design review 10A):**
  - Keys:
    - `academySettings.<code>.label` and `.description`
    - `.options.<value>` for enum controls
    - `.unit` for number controls
    - A shared range hint `academySettings.range` ("{min}–{max} {unit}")
  - `tests/i18n-parity.test.ts` covers all of these in en + ar.
  - Components:
    - boolean → `Switch`
    - enum → `Select`
    - number → `Input` inside `InputGroup` with the unit addon at inline-end
    - "Custom" → `Tag`
    - confirmations → `AlertDialog`
    - no new kit components
- **Mobile (design review 11A):**
  - Preference rows are `flex-col` below `sm`. A switch stays inline at inline-end; a Select or number input goes full width under the label.
  - Touch targets are at least 44px.
  - Below `md`, the Academies table shows only the Academy and Plan columns. Email, students and granted move to an expandable row detail.
  - No horizontal scroll at 375px.
- **Accessibility + RTL (design review 12A):**
  - Number inputs normalise Arabic-Indic (٠-٩) and Persian (۰-۹) digits to Latin before the Zod parse, using a shared helper with unit tests. Values display in the page locale.
  - Every control has `<Label htmlFor>`, so tapping a label toggles its switch. The effect hint is linked through `aria-describedby`.
  - The reapply and plan-change `AlertDialog`s focus Cancel first.
  - Academy names are `dir="auto"` and emails `dir="ltr"`. Dates use `Intl` with the page locale.
  - Every control has a focus-visible ring, and hints meet 4.5:1 contrast.
  - The `Switch` already has RTL variants, so nothing new is needed there.
- **Save model (design review 3A):**
  - `appliesTo: "future"` switches and selects save on change. The update is optimistic, followed by a "Saved" toast; on failure the value rolls back and an error toast shows.
  - Reapply settings and all number fields use a staged value plus a Save button.
  - A reapply Save opens an `AlertDialog`: "This updates upcoming classes. Continue?"
  - While a save is pending, the control is disabled and shows a spinner.
- **States (design review 4A):**

  ```
  FEATURE              | LOADING              | EMPTY                 | ERROR                                   | SUCCESS               | PARTIAL
  ---------------------|----------------------|-----------------------|-----------------------------------------|-----------------------|---------------------------------------
  Preferences card     | Skeleton row / entry | Registry empty: card  | Inline destructive Alert + Retry        | Rows render           | Teacher/student: card hidden
                       |                      | hidden (no empty card)| (translated key, never error.message)   |                       |
  Row value            | Control disabled +   | Default: no tag       | Rollback + error toast (translated)     | Toast "Saved"         | Custom: Tag "Custom" + default shown
                       | spinner while saving |                       |                                         |                       | as hint + "Reset to default" (confirm)
  ```
- Every string is i18n'd in en + ar, with RTL-safe logical properties.
- Runs through the `/ui-scan --plan` → `/ui-scan` gate.

### Platform owner (R1, R8)

- `users.isPlatformOwner` (boolean, default false) is set true for Mohamed's account by a custom data migration. There's a new `platformOwnerProcedure` on `protectedProcedure`.
- Deployment settings (`settings.list` / `settings.update`, the Meetings keys) require the platform owner. The integration section on `/platform` (formerly `/settings`) renders only for the owner. No env vars, no allowlist.
- `platform.setOrganizationPlan({ organizationId, plan })` is owner-only, and it's the one route deliberately allowed to name another org. It's audited with `organizations.planGrantedBy` / `planGrantedAt`, and an owner-only "Academies" section lists academies with a plan select. `PLAN_LIMITS` follow the granted plan.
- Deferred (R7): gating Meetings behind a paid plan goes to the Billing & Paymob spec (TODOS.md).
- **Academies list (design review 9A):** a `DataTable` in server mode, the same kit as the Members table.
  - Columns:
    - **Academy:** name (`dir="auto"`) + `shortCode`.
    - **Admin email:** `dir="ltr"`.
    - **Plan:** a `Select` that opens the 6A confirm.
    - **Students:** used/limit.
    - **Granted:** "by <email>, <locale date>" or "—".
  - Search by name or email, 20 per page, newest first. A "Yours" `Tag` marks the owner's own academies.
  - States: skeleton rows while loading; `EmptyState` "No academies yet" when empty; an inline destructive `Alert` + Retry on error.
  - This needs a platform-owner `platform.listOrganizations` query (paginated, searchable).
- **Plan change flow (design review 6A):**
  - Picking a plan opens an `AlertDialog` naming the academy and the change, e.g. "Free → Basic".
  - For each limit the new plan is below current usage, a warning `Alert` reads: "80 students, above the 50 limit: they keep access, but no new students can be added."
  - Downgrades are allowed, and existing data is never touched.
  - After Confirm the row shows pending, then a "Plan updated" toast. Errors use translated keys. Cancel leaves the select unchanged.
- **After a grant (design review 7B):**
  - When `organizations.planGrantedBy` is set, `PlanUsageCard` replaces its "Paid plans with higher limits are coming soon" line with "Plan provided by Gateling" (en + ar).
  - Granting invalidates `organizations.getActive` and `organizations.usage`, so the owner's own academy updates at once.
  - An Inngest function (`on-organization-plan-granted`) emails the academy's admins about the new plan in their locale (en + ar templates, Nodemailer). The grant itself never waits on the email.
- **Owner page (design review 2A):** `organizations.getActive` exposes `isPlatformOwner`. The sidebar item for the owner page shows only when it's true, labelled "Platform" (en + ar). The page lives at `/platform` and holds the Integrations (Meetings) card and the Academies section. A non-owner who opens the URL gets `EmptyState` with the new copy `settings.ownerOnly`, never the error `Alert`. The old `settings.adminOnly` copy is retired.

### Build rule

The engine PR ships with **at least one setting whose `requestedBy` names a real academy**. An engine with zero settings, or with speculative ones, doesn't merge.

## Open Questions

1. Which behavior becomes the first setting? None has been proven yet (her requests are features). It will likely come out of onboarding academy #2.
2. Do `timeZone` and `currency` move into the registry, or stay as columns? Recommendation: leave them. They're structural and indexed by other logic, and moving them buys nothing now.

Findings:

7. **[P1] (confidence 8/10)** DT3 / design 5A, all-or-nothing reapply (Architecture). The design fixes the behavior but not the mechanism. A DB write and `inngest.send` can't share one transaction, so there are two ordering failure modes. Send first, then the commit fails: an event fires for a value that was never stored.
